# russia-flights — контекст проекта

## Что это
Интерактивная карта (Leaflet) прямых международных рейсов из городов России.
Данные обновляются автоматически через GitHub Actions, без ручного вмешательства в штатном режиме.

Репозиторий: github.com/xkonstantinnnx/russia-flights

## Архитектура данных
Конвейер из источников. Правило: каждый следующий источник ТОЛЬКО ДОБАВЛЯЕТ данные, никогда не удаляет.

1. **AirLabs** (`run_airlabs_primary`) — основной источник, все аэропорты, постраничная загрузка `limit=50&offset=N`.
2. **AeroDataBox** (через RapidAPI) — дополняющий источник, фильтр `countryCode != RU`.
3. **OpenSky** (`run_opensky_additive`) — дополняющее обогащение, только добавляет записи.
4. **Яндекс.Расписания** — третий дополняющий источник (введён после отключения gogov.ru).

Обработка в два этапа: **Stage1 → Stage2**, с ранним выходом (early exit) на Stage1.
Перед запуском текущий `routes.json` загружается с диска; маршруты, не найденные ни одним источником, удаляются — это единственное место, где данные пропадают. Удаление применяется только к городам, которые AirLabs реально опросил: города, не опрошенные из-за лимита квоты или сбоев запросов, сохраняют текущие маршруты (защита от потери данных при частичном отказе источника).

## Деплой
- Прод: https://russia-flights.ru/ — виртуальный (shared) хостинг Timeweb.
- GitHub Actions (`update.yml`) только обновляет `routes.json` и пушит в репозиторий. Прямой FTP-деплой из этого workflow убран 2026-04-15 после серии падений `Timeout (control socket)` на всех протоколах (FTP/FTPS/SFTP) — похоже, файрвол Timeweb блокирует AWS IP-диапазон раннеров целиком, не только SSH.
- Единственный реальный механизм публикации на прод — Crontab самого виртуального хостинга russia-flights.ru: ежечасный `curl`, забирающий свежий `routes.json` из GitHub по raw-URL. Это не резервный, а ОСНОВНОЙ путь деплоя.
- SSH-доступ к виртуальному хостингу — через локальный `~/.ssh/config` (алиас `timeweb-shared`, ключ `~/.ssh/timeweb_shared`); реквизиты (user/host) в репозитории не хранятся. Сайт живёт в `~/russia-flights/public_html/`. Команда `crontab` на хостинге отключена совсем (выводит «Редактирование cron-задач доступно только через Панель Управления Аккаунтом» — проверено 2026-08-14, в т.ч. с `ssh -t`); смотреть и править cron можно только в веб-панели Timeweb. Захардненный вариант cron-команды — `scripts/routes_pull.sh` (источник истины в репозитории, на хостинге лежит в `~/russia-flights/routes_pull.sh`, вне public_html): temp-файл → валидация JSON → атомарный mv.
- `index.html`/`ads.txt` (и вообще всё, кроме `routes.json`) на прод сами не попадают — только ручной `scp <файлы> timeweb-shared:~/russia-flights/public_html/`. Работает, проверено 2026-08-02. Каждый такой деплой — отдельное подтверждение пользователя, см. правило ниже. Полный список выкладываемого руками: `index.html`, `privacy.html`, `fonts.css`, каталог `fonts/` (self-host шрифты с 15.08.2026), `og-image.png`, `sitemap.xml`, `ads.txt`, `.htaccess`, `.well-known/security.txt` (каталог на хостинге уже создан).
- Классификатор авторежима иногда блокирует `scp` на `timeweb-shared` — недетерминированно, та же команда через минуту проходит. Обходить другими инструментами не пытаться: попросить пользователя выполнить `! scp ...` самому (вывод попадёт в беседу), дальше проверять результат обычными curl/ssh.
- Если прямой SSH до `timeweb-shared` не проходит после 2-3 повторов (`Connection reset by peer` / таймаут на banner exchange), а другие SSH-цели с той же сети отвечают нормально — это не блокировка сети целиком, а что-то на маршруте именно до этого хоста (проверено 12.08.2026). Рабочий обходной путь — ProxyJump через `timeweb-flights-vps` (иначе к этому проекту не относится, но как прыжок сработал): `ssh -J timeweb-flights-vps timeweb-shared "..."` / `scp -J timeweb-flights-vps <файлы> timeweb-shared:~/russia-flights/public_html/`. Подробности диагностики — `~/projects/claude-code-setup/CLAUDE.md`, раздел «Сетевая архитектура». Это тоже обходной путь мимо обычного канала — подтверждать у пользователя каждый раз отдельно, не как разовое разрешение на всю сессию.
- В `~/russia-flights/public_html/` на хостинге лежит брошенный `.git` (remote прописан на этот репозиторий, но «No commits yet» — реальные файлы туда попали через FTP, не через git). Не использовать `git pull` там, это нерабочая заготовка. `.htaccess` блокирует внешний доступ к `.git/`, `README.md`, `update_routes.py`, `.ftp-deploy-sync-state.json` — чистить не обязательно. С 2026-08-14 источник истины для `.htaccess` — корень репозитория (редиректы HTTP→HTTPS/www→apex, security-заголовки, HSTS, CSP Report-Only); на прод попадает только ручным `scp`, как index.html. Бэкап доаудитной версии на хостинге: `.htaccess.bak-2026-08-14`.
- Диагностические workflow `Test SSH` (`main.yml`) и `Тест всех вариантов деплоя Timeweb` (`test_proxy.yml`) удалены 2026-08-14 по итогам security-review: все методы деплоя из CI (FTP plain/FTPS×2/SFTP/rsync) падали ещё с 2026-04-12, а workflow держали живые FTP/SSH-креды прода в сторонних actions. Не предлагать SSH/FTP-деплой из CI и не восстанавливать эти workflow. Секреты `FTP_*`, `SSH_*`, `PROXY_URL` подлежат удалению руками (см. правило про секреты ниже), FTP-пароль и SSH-ключ — ротации в панели Timeweb.

## Жёсткие правила для index.html
- `loadRoutes()` обязан проверять пустой `routes.json` и откатываться на `SEED`.
- `const RU_COORDS` должен быть объявлен ДО блока `/* ── MARKERS ── */`.
- `function getRUCoords` идёт сразу после `RU_COORDS`.
- Не менять порядок этих блоков даже при рефакторинге — от этого зависит инициализация карты.
- Номер версии — при ЛЮБОМ заметном изменении index.html (новая фича, фикс
  поведения UI, не косметическая правка вроде опечатки) обязательно
  увеличивать в этом же коммите. Это единственный способ на глаз отличить,
  какая версия карты сейчас на проде/превью — если не бампать, бейдж теряет
  смысл. Мест ДВА, менять оба (id `#version-badge` не существует, не искать):
  бейдж в `.panel-footer-links` и ячейка «ВЕРСИЯ» в `renderAbout()`.
  Текущая — v3.9.
- Слой «Яндекс» — официальный Tiles API (`tiles.api-maps.yandex.ru`), ключ в
  `YANDEX_TILES_KEY`. Тариф бесплатный, суточный лимит не ограничен, платы за
  превышение нет (потолок — 30 запросов в секунду), поэтому утечка ключа не
  создаёт денежного риска; ключ и так виден в HTML, это нормально. Ограничение
  по домену в кабинете на 15.08.2026 найти не удалось: документация описывает
  кнопку «Изменить», которой в интерфейсе нет, а «Настроить» открывает только
  имя и секреты (секреты — для подписи запросов, статическому сайту не нужны).
  `projection=web_mercator` и `l=map` обязательны.
- Набор слоёв с 15.08.2026 полностью легальный и состоит из трёх схем:
  `yndx` (Tiles API), `osm` (tile.openstreetmap.org), `topo` (OpenTopoMap,
  CC-BY-SA, вернулся после включения атрибуции). Слои Google — схема,
  спутник, гибрид — удалены: брались с внутренних `mt{s}.google.com` в обход
  ToS. **Спутника в наборе нет и бесплатно не будет:** Tiles API его не
  отдаёт, Esri World Imagery и бесплатный тариф MapTiler — только
  некоммерческие проекты, Google Map Tiles API платный с биллингом. Вернуть
  спутник = платный тариф, отдельное решение. CARTO как тёмная подложка тоже
  не подходит — для коммерческого использования требует лицензию Enterprise.
  При добавлении слоя не забыть про CSP в `.htaccess` (`img-src`).
- Атрибуция источника тайлов (контрол Leaflet внизу слева) обязательна по
  условиям всех провайдеров — не прятать снова. До 15.08.2026 она была
  скрыта (`display:none` + `attributionControl:false`), из-за чего пришлось
  выкинуть слой OpenTopoMap. Текст копирайта берётся из поля `attribution`
  у записи в `TILES`; у нового слоя оно обязательно. Фильтр `.rf-dark-map`
  висит на слое тайлов и атрибуцию не задевает — так и оставить.
- Маркировка рекламы (ФЗ-38, ст. 18.1) — не удалять и не «упрощать»: параметр
  `erid` в `tpLink()` (значение в `TP_CONFIG.erid`) и видимая строка
  `TP_AD_LABEL` («Реклама. Go Travel Un Limited. ИНН 9909520797») рядом с
  кнопкой в карточке. Обе части обязательны вместе: токен в ссылке и пометка
  с рекламодателем на странице. Новый erid выдаёт Travelpayouts при смене
  юрлица рекламодателя — тогда обновлять оба места. Верификация сайта в TP
  (вкладка Drive) для этого НЕ нужна и делать её не надо: единственный
  предлагаемый способ — сторонний скрипт `emrldtp.com`, который обнуляет
  href наших же партнёрских ссылок и патчит DOM (разбор — 15.08.2026).
- Данные из routes.json и сгенерированных блоков вставлять в DOM только через
  `esc()`. Для ссылок дополнительно `safeUrl()` (пропускает только `https://`):
  `href="${esc(safeUrl(u))}"`. Инлайновые `onclick` со значениями из данных не
  использовать — `esc()` экранирует HTML, но внутри атрибута браузер декодирует
  сущности до разбора JS, и `&#39;` снова становится кавычкой; вместо этого
  data-атрибут + делегированный обработчик (см. чипы аэропортов).

## Безопасность (итоги аудита 14.08.2026)
- **Главное правило для `scripts/gen_*.py`:** генераторы пишут данные ВНУТРЬ
  `<script>` в index.html (`const X = {...};`, JSON-LD). Это исполняемый
  контекст: `json.dumps` не трогает `</script>`, и имя города или описание из
  Википедии вида `</script><img src=q onerror=...>` вырывается из скрипта и
  становится разметкой (хранимый XSS, воспроизведён в браузере до фикса).
  Для ЛЮБОЙ такой вставки использовать `json_for_script()` из
  `scripts/_js_embed.py` — новый генератор тоже. Клиентский `esc()` здесь не
  помогает (он про вставку в DOM), CSP тоже: из-за инлайн-скриптов в политике
  обязателен `'unsafe-inline'`.
- Проверять такой фикс только сквозным тестом (отравленное имя → генератор →
  браузер). Признак пробоя — сырой `<img>` в документе, а НЕ наличие
  `</script>` внутри JSON-LD: нежадный regex сам останавливается на внедрённом
  теге, и обрезанный кусок выглядит чистым. В JSON-LD попадают только топ-5
  направлений, поэтому отравленное имя надо добавлять во все города.
- `.htaccess` (в репозитории) даёт редиректы HTTP→HTTPS и www→apex, HSTS,
  nosniff, X-Frame-Options, Referrer-Policy, Permissions-Policy и CSP в режиме
  **Report-Only**. Перевод CSP в боевой режим — после обкатки; в политику
  сознательно не внесены рекламные пиксели (yandex.ru/an, doubleclick),
  которые при включении отвалятся — Метрике это не мешает.
- Репозиторий: branch protection на `main` (запрет force-push и удаления;
  required reviews НЕ включать — сломает автопуш `routes.json` из Actions),
  Dependabot alerts + security updates, все actions приколоты к SHA-коммитам —
  держать так, теги обратно не возвращать.
- Секреты в пайплайне печатать нельзя даже частично: в логах только
  «доступен / не настроен».
- Превью GitHub Pages не публикует пути на точку (сборка типа legacy),
  поэтому `/.well-known/security.txt` там отдаёт 404, хотя на проде работает.
  `.nojekyll` это НЕ чинит (он про каталоги на подчёркивание). Расхождение
  осознанное, чинить не надо.

## Инфраструктура для отладки (только личная, не рабочая)
- Логи пайплайна — через GitHub Actions: `gh run list`, `gh run view <id> --log`.
- Личный VPS, алиас `timeweb-flights-vps` в `~/.ssh/config` — НЕ имеет отношения к деплою russia-flights. Это отдельный сервер с другими личными проектами (russiametro, vikunja, openproject, zabbix); cron/скриптов для этого проекта там нет.
- Cron, реально публикующий прод, живёт в Crontab виртуального хостинга russia-flights.ru — туда нет SSH-доступа (см. «Деплой»).
- В этом проекте нет и не будет доступа к рабочей/корпоративной инфраструктуре — только этот VPS и GitHub.

## Чего агенту нельзя делать без явного подтверждения
- `git push` в любую ветку.
- Запуск workflow вручную (`gh workflow run`).
- Любые изменения FTP-credentials и секретов в GitHub Actions — это всегда руками, не агентом.
- Удаление маршрутов из `routes.json` напрямую (только через штатный пайплайн).
- Деплой на прод (`scp`/`ssh` на `timeweb-shared`, копирование `index.html`/`ads.txt` и любых
  файлов в `~/russia-flights/public_html/`) — подтверждать КАЖДЫЙ раз отдельно. Разовое «деплой»
  в рамках сессии разрешает ровно тот один деплой, а не последующие — даже следующий коммит в той
  же беседе требует нового явного запроса.
