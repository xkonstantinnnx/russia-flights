# Что осталось сделать

Список ведётся с 08.08.2026, после сверки реализованного сайта с макетом
Claude Design (handoff от 08.08.2026). Всё, что здесь перечислено, обсуждено
и отложено осознанно — это не забытые баги.

## Требует данных, которых пайплайн пока не собирает

### Статус маршрута: «НОВОЕ» / «ОТМЕНЁН»
В макете — тег в строке списка и цветной блок в карточке («Новое направление —
появилось в марте 2026», «Рейсы приостановлены с ноября 2025»).

Откуда брать: git-история `routes.json` — первое и последнее появление пары
«город→направление», тем же приёмом, что уже работает в
`scripts/gen_network_trend.py`.

Подводные камни, из-за которых это не сделано сразу:
- в истории есть период битых данных (25.03–06.04.2026, всплеск до ~45
  маршрутов на город) — его надо отфильтровать, как это уже делает
  `gen_network_trend.py` через `MAX_SANE_ROUTES_PER_CITY`;
- пайплайн сам временами теряет маршруты при деградации источников (см.
  прогон 07.08.2026), поэтому нужен порог вроде «отсутствует в 2+ прогонах
  подряд», иначе появятся ложные «отменён».

### Сезонность расписания (год / лето / зима)
В макете это чип ЛЕТО/ЗИМА в списке и полоса из 12 месяцев в карточке,
означающие, **когда рейс летает**. Сейчас в этих местах — климатический
комфорт направления (`SEASON_DATA`, Open-Meteo), это другая метрика; так
решено осознанно, но расхождение с макетом остаётся.

Чтобы появилась настоящая сезонность расписания, нужен либо источник годовых
расписаний, либо накопление помесячных снапшотов присутствия маршрута в
течение года (раньше чем через год данных не будет).

## Отложено целиком

### Форма обратной связи (сообщить об ошибке)
Пользователи должны иметь возможность сообщить об ошибке в данных (неверная
сезонность, визовый режим, маршрут и т.п.) — сейчас такого канала нет.
Нужно:
- сама форма (город/направление, текст, опционально email для ответа);
- защита от спама — минимум honeypot-поле + rate-limit на бэкенде, в
  идеале капча только при подозрительной активности, чтобы не мешать
  обычным пользователям;
- куда складывать обращения — GitHub Issues через API (токен только на
  бэкенде, не в клиентском JS) или тот же backend/serverless, что решится
  для admin-панели (см. ниже) — решение единое, не заводить два разных
  бэкенда под разные формы.
Добавлено в бэклог 12.08.2026 по запросу пользователя, не реализовано.

### Второй источник карты: векторные тайлы
Запрошено пользователем 15.08.2026 — не хочет зависеть от единственного
поставщика. Сейчас слой ровно один (Яндекс Tiles API), и второго легального
**растрового** источника не существует: у зарубежных границы России не по
российскому законодательству, а российские альтернативы либо платные и
векторные (2ГИС), либо по договору (RuMap); тайловые серверы OSM у Рамблера
закрылись 01.09.2024.

Реальный путь — **векторные** тайлы: стиль применяется в браузере, поэтому
слой границ можно не рисовать вовсе, и тогда некорректных границ на карте
физически нет. Кандидат — **OpenFreeMap**: лицензия MIT, публичный инстанс
без ключа, регистрации и лимитов, коммерческое использование разрешено,
при желании ставится на свой сервер (подошёл бы `timeweb-flights-vps`).
Запасной вариант — Protomaps (self-host одного файла pmtiles).

Объём работ: переезд с растрового `L.tileLayer` на MapLibre GL (либо мост
между ними), своя правка стиля с выключенным слоем административных границ,
возврат переключателя слоёв, атрибуция OpenFreeMap/OSM. Дуги маршрутов и
маркеры сейчас — объекты Leaflet, их тоже придётся переносить.

Проверить у юриста до внедрения: вывод «не показывать границы вовсе безопаснее,
чем показывать чужие» — это рассуждение, а не норма закона.

### Admin-панель
Экран входа + таблица CRUD по направлениям + форма добавления (в макете есть
полностью). Решения, принятые до отладки и остающиеся в силе:
- персистентность — отдельный backend/serverless, не GitHub API и не
  localStorage; конкретная платформа не выбрана (кандидат — личный VPS
  `timeweb-flights-vps`);
- авторизация — настоящая серверная проверка пароля, не JS-гейт;
- защита ручных маршрутов от автопайплайна **не делается** — риск принят
  осознанно (такой маршрут сотрёт ближайший прогон, если ни один источник его
  не подтвердит).

### История обновлений маршрутов в админке
Запрошено пользователем 15.08.2026. В админке нужен экран, показывающий, что
менялось в маршрутах от прогона к прогону (пайплайн отрабатывает дважды в
месяц, 1-го и 15-го): за каждый прогон — дата, сколько маршрутов добавилось,
сколько исчезло, и списком сами пары «город→направление» с обеих сторон.

Данные брать не из нового сбора, а из git-истории `routes.json` — тем же
приёмом, что уже работает в `scripts/gen_network_trend.py`. Оттуда же
переиспользовать два фильтра, иначе история будет врать:
- период битых данных 25.03–06.04.2026 (всплеск до ~45 маршрутов на город)
  отсекается порогом `MAX_SANE_ROUTES_PER_CITY`;
- пайплайн временами теряет маршруты при деградации источника, поэтому
  «исчез» показывать осторожно — либо помечать как возможный сбой источника,
  либо считать выбывшим только после 2+ прогонов подряд.

Пересекается с пунктом «Статус маршрута НОВОЕ/ОТМЕНЁН» выше: там та же
git-история нужна для тегов на публичной части сайта. Считать общей
подзадачей — один разбор истории, два потребителя.

### Мониторинг проблем с данными
Экран в админке, показывающий расхождения и дыры в данных сайта — без него
проблемы вроде «4 направления без сезонности» (см. ниже) находятся только
случайно, руками. Минимальный набор проверок:
- **направления без SEASON_DATA** — направление есть в `routes.json`, но
  отсутствует в `SEASON_DATA` (обычно значит: появилось в пайплайне после
  последнего ручного прогона `gen_season_data.py`, который не автоматический,
  см. `CLAUDE.md`/докстринг скрипта). Обнаружено вручную 09.08.2026 — было 4
  таких направления (Варадеро, Кабул, Багдад, Нахичевань), исправлено
  прогоном скрипта, но механизма замечать это автоматически нет;
- то же самое для `CITY_INFO` (Wikidata/wikipedia, `gen_city_info.py`),
  `TOURISTER` (`gen_tourister_links.py`) и `VISA_REGIMES` — все четыре блока
  генерируются вручную отдельными скриптами и могут так же незаметно
  расходиться со свежими направлениями из `routes.json`;
- маршруты, пропавшие из `routes.json` при деградации источника (см. «Открытые
  вопросы по данным» ниже) — сравнение с предыдущим снапшотом git.

Наиболее вероятная реализация — не отдельный сбор данных, а разовая сверка
(«направления из routes.json» minus «ключи каждого из четырёх блоков»),
которую можно и встроить в один из существующих gen_*.py как `--check`, и
показать в самой админке как список проблем при заходе.

## Открытые вопросы по данным

- **Ручные маршруты не переживают пайплайн.** «Москва → Занзибар» удалялся уже
  дважды: его не подтверждает ни один источник, а Москву AirLabs опрашивает
  каждый прогон. 09.08.2026 возвращён в третий раз (рейс реальный — Air
  Tanzania из Внуково со 02.07.2026 по 24.10.2026). Пока нет механизма
  «закреплённых» маршрутов, он будет исчезать снова после каждого прогона,
  где ни один источник его не увидит.

- **MANUAL_APT_OVERRIDE (`scripts/gen_route_details.py`) может устареть молча.**
  Единственный источник аэропорта вылета из многоаэропортного города — снэпшот
  Jonty; для маршрутов, которых там нет (обычно чартеры/новые направления),
  добавлено ручное исключение — 12.08.2026 так зафиксирован Занзибар (VKO,
  Air Tanzania). Если авиакомпания сменит аэропорт вылета, запись останется
  висеть неверной — никакой проверки/оповещения нет, как и для остальных
  вручную подтверждённых фактов в проекте (см. пункт выше про Занзибар и
  визовые режимы). Проверять глазами при следующем ручном пересборе
  `gen_route_details.py`, если появится повод усомниться.
